# Spike 0.5: LLM inside a Durable Object

**Question:** can a DO run **one LLM step at a time**, with tools, through Effect AI, using Workers
AI and AI Gateway as providers? Can we persist the conversation between steps and replace the
model with a scripted one in tests?

**Timebox:** 1.5 days. **Size:** M. **Depends on:** 0.1. **Informs:** D5, D6.

## Why it matters

LLM agents are first-class (M2). The durability design (D6) treats a turn as a state machine:
`model_call → tool_call* → model_call → … → final`. **Each step is persisted before the next one
is scheduled.** That only works if:
1. we can make a model call that **returns tool calls without running them automatically**, or
   runs exactly one round, so we can checkpoint between the model call and the tool execution;
2. the prompt/transcript **serializes to JSON and back** without loss (tool calls, tool results,
   ids);
3. the provider is a swappable **Layer**, so tests are deterministic and cost nothing;
4. a model call fits within DO limits. Awaiting `fetch` is wall time, not CPU, but check this.

## What the docs say (2026-11-25)

- Workers AI: `const ai = yield* Cloudflare.Workers.AI()` in the construction phase. Provide
  `Cloudflare.Workers.AIBinding`. `ai.run(model, {...})` is the raw call.
  **`ai.model({ model, parameters })` returns an Effect AI `LanguageModel` layer.** Example model:
  `@cf/meta/llama-3.3-70b-instruct-fp8-fast`.
- AI Gateway: the `Cloudflare.AI.Gateway` resource. `aiGateway.model({...})` has the same
  `LanguageModel` shape. (The gateway page hasn't been read yet; read it first.)
- Effect AI: the `LanguageModel` and `Chat` services; `LanguageModel.generateText` / `streamText`.
  Import path confirmed in effect 4.1.5: **`effect/ai`** (`LanguageModel`, `Tool`, `Toolkit`, `Prompt`,
  `Chat`, `Response`, `McpClient`, …).

## Probe setup

An `LlmProbe` DO in `spikes/src/llm.ts` with:
- a toolkit of two tools:
  - `lookup_order({ orderId })`, which returns a fixed fake order and **logs every execution**
    to a SQLite table (so we can count re-executions)
  - `current_time()`
- a `transcript` table `(session_id, seq, kind, json)`, where `kind` is `user`, `model`,
  `tool_call`, or `tool_result`
- RPC: `prompt(sessionId, text)` runs a whole turn in this spike, for simplicity, and
  `step(sessionId)` runs exactly one step
- routes `POST /llm/:provider/:session` with `{ text }`, and `GET /llm/:session/transcript`

## Design sketch to validate (feeds M2)

```ts
// One step of a turn, run by the "step" durable callback.
step(sessionId) = transaction-safe:
  last = transcript.last(sessionId)
  if last is user | tool_result      → call model (no auto tool resolution)
                                      → persist model message (+ tool calls) → schedule step
  if last is model with pending tool calls
                                      → run ONE pending tool (idempotency key:
                                        sessionId/seq/toolCallId) → persist tool_result
                                      → schedule step
  if last is model with final text    → mark turn complete → notify waiters
```

Open design questions to answer from the results:
- Run tool calls one per step or all in one step? One per step is more durable; all at once has
  less overhead. Probably one per step, unless L9 shows the overhead matters.
- Where do token budget and step cap live (session row)?
- Should the provider be configured per agent (`model: AgentModel.workersAI(...)` in the agent
  definition) or per platform? Probably per agent, with a platform default.

## Risks and fallbacks

| Risk | Fallback |
|---|---|
| Effect AI can't skip tool resolution | Stub-handler toolkit plus our own dispatch (L2) |
| `Prompt` doesn't round-trip | Our own transcript schema, converted to and from `Prompt` on each step |
| Workers AI tool calling is unreliable | Default to AI Gateway with a hosted frontier model; keep Workers AI for cheap tests |
| Streaming over DO RPC fails | Stream from the Worker, reading new transcript rows, or push through a hibernatable WebSocket (M7) |

| L9 | Llama 3.3: a model step takes **0.6–1.8 s** (typically ~0.9 s), about 10.8 neurons for the tool-call round and 13.4 for the answer round, 273/17 and 325/23 tokens in/out. | L10 | **(a) Bad tool arguments:** with resolution enabled or with strict validation, the **whole** `generateText` call fails with `AiError` (`ToolParameterValidationError` / `InvalidOutputError`), and the model never sees the error. With `toolCallValidation: "deferred"` it succeeds and returns the raw invalid arguments; the step loop validates them when the tool step runs and records a failed tool result the model can correct. **(b) Provider errors are swallowed:** an unknown model or a deprecated one returns **success** from the adapter: empty text, finish reason `stop`, no `AiError`. **Effect AI import paths and versions:** effect 4.1.5 exports `effect/ai/LanguageModel`,
`Prompt`, `Response`, `Tool`, and `Toolkit` as modules (also re-exported from `effect/ai`).
Tool handlers must have no requirements (`R = never`). A tool that needs services declares
them with `Tool.make(name, { dependencies: [Service] })`, and the caller provides them per call.
That's how M2 tools get `Workspace` and `AgentContext`.

**Gotchas:**
- `alchemy dev` creates a **real** AI Gateway in the cloud (gateways have no local emulation).
  So do `dev: true` tests, in `test_$USER`, which are destroyed afterwards.
- `Cloudflare.AI.Gateway` plans an `update` with "no declared property changes" on every plan, so
  a stack with a gateway is never clean.
- Workers AI runs under `alchemy dev` by calling the real service, which bills neurons.
- In the probe, `import type * as Response from "effect/ai/Response"` shadows the global
  `Response`. The bundler doesn't typecheck, so it deployed anyway.

**Verdict on D5 / D6:**
- **D5: confirmed, with caveats.** Effect AI `LanguageModel` plus `Toolkit` is the right
  abstraction, and the provider really is a Layer (Workers AI, gateway, or scripted). Default
  to Llama 3.3 70B or Mistral Small 3.1 on Workers AI. Around Alchemy's beta.87 adapter, the
  framework must:
  1. treat an empty response as a failure (provider errors are swallowed)
  2. get structured output through a forced `respond` tool, not `generateObject`
  3. stream transcript steps rather than raw tokens until the streaming bug is fixed

  Anthropic or OpenAI through the gateway is an open item (key plus provider package).
- **D6: confirmed.** One step per durable callback (a model call with resolution disabled, or
  one tool call), persisted before the next is scheduled with an increasing `progress`, survives
  failures and redeploys without repeating tools. One tool call per step: tool steps cost about
  0 ms plus about 150 ms of scheduling, small next to a ~1 s model call. Validate tool arguments
  in the tool step (deferred validation), so bad arguments become a failed tool result the model
  sees, not a failed turn.
