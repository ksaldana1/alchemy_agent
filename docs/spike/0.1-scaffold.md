# Spike 0.1: Scaffold

**Question:** can we build, run locally, deploy, redeploy, and destroy an Alchemy v2 stack
(one Worker + one SQLite Durable Object) with Bun and pinned versions?

**Timebox:** half a day. **Size:** S. **Blocks:** every other spike.

## Why it matters

Everything else depends on a repeatable dev → deploy loop. There is also a known trap:
Alchemy now deploys DO classes with the Worker `exports` map. A Worker deployed this way cannot
go back to the old `migrations` flow, and older Alchemy releases can't redeploy a Worker that a
newer release has deployed. So **we pin exact versions from day one and only upgrade on purpose.**

## Prerequisites

- Bun (latest stable). Alchemy also supports Node ≥ 24.11.1, but we're using Bun.
- A Cloudflare account. SQLite-backed DOs work on the free plan. Workers AI and Queues may need
  Workers Paid; 0.6 confirms this.
- Credentials: `alchemy profile edit --add Cloudflare`, which stores them in
  `~/.alchemy/profiles.json`. This step is interactive, so run it yourself with
  `! bunx alchemy profile edit --add Cloudflare` in the Claude session.

## Code sketch

The API shapes come from the Alchemy docs as read on 2026-11-25. **Import paths for HTTP types
(`HttpServerResponse`, `HttpServerRequest`) are not confirmed.** In Effect 4 they may live under
`effect/unstable/http`. Check the Workers page examples or the type definitions.

```ts
// spikes/src/counter.ts
import * as Cloudflare from "@alchemy.run/cloudflare";
import * as Effect from "effect/Effect";

export default class Counter extends Cloudflare.DurableObject<Counter>()(
  "Counter",
  Effect.gen(function* () {
    const state = yield* Cloudflare.DurableObjectState;          // construction phase
    return Effect.gen(function* () {                              // per instance
      let count = (yield* state.storage.get<number>("count")) ?? 0;
      return {
        increment: () => Effect.gen(function* () {
          count += 1;
          yield* state.storage.put("count", count);
          return count;
        }),
        get: () => Effect.succeed(count),
      };
    });
  }),
) {}
```

```ts
// spikes/src/worker.ts
export default Cloudflare.Worker(
  "SpikesApi",
  { main: import.meta.url },
  Effect.gen(function* () {
    const counters = yield* Counter;
    return {
      fetch: Effect.gen(function* () {
        // parse /counter/:name/(increment|get) from the request, then:
        const n = yield* counters.getByName(name).increment();
        return HttpServerResponse.json({ name, count: n });
      }),
    };
  }),
);
```

```ts
// spikes/alchemy.run.ts
export default Alchemy.Stack(
  "Spikes",
  { providers: Cloudflare.providers(), state: Cloudflare.state() },
  Effect.gen(function* () {
    const api = yield* SpikesApi;           // verify: how a Worker is yielded into a Stack
    return { url: api.url };
  }),
);
```

Open questions to settle while writing it:
- How the Worker is referenced from the Stack (is the default export enough, or must it be yielded?).
- How to read the request path inside `fetch` (the `HttpServerRequest` service?).
- Whether `workersDev: true` is needed to get a public URL.

## Steps

1. Scaffold the workspace and install pinned deps. `bunx tsc -b` passes.
2. `bunx alchemy dev` (from `spikes/`). `curl localhost:<port>/counter/a/increment` twice
   returns 1, then 2. Stop dev, restart it: the count continues (local DO SQLite persists, or
   find out that it doesn't and write that down).
3. `bunx alchemy deploy --stage dev_$USER`. Write down the URL and how long the deploy took.
4. Increment `a` three times on the deployed URL.
5. Change the response shape a little (add a `v: 2` field) and redeploy. `get` still returns 3,
   and the response shows `v: 2`.
6. `bunx alchemy plan --stage dev_$USER` shows no changes.
7. Add a minimal cloud test with `@alchemy.run/test/Bun`:
   ```ts
   const { test, beforeAll, deploy } = Test.make({
     providers: Cloudflare.providers(), state: Cloudflare.state(),
   });
   const stack = beforeAll(deploy(Stack));
   test("increments", Effect.gen(function* () { /* HttpClient → stack.url */ }));
   ```
   Run it once against `test_$USER`, and once with `ALCHEMY_TEST_DEV=1` (local).
8. `bunx alchemy destroy --stage test_$USER` cleans up.
9. Add root scripts: `dev`, `deploy`, `destroy`, `typecheck`, `test`, `test:cloud`.

## Done when

- [x] `alchemy dev` and the deployed stage both serve `/counter/:name/increment`.
- [x] The count survives a redeploy.
- [x] The Bun test harness passes both locally (`dev: true`) and in the cloud.
- [x] Exact versions are pinned and recorded below.

## Risks and fallbacks

| Risk | Fallback |
|---|---|
| The Bun test adapter doesn't work with our setup | Use the Vitest adapter (`@alchemy.run/test/Vitest` + `@effect/vitest`), run with `bunx vitest`. |
| Local DO state doesn't persist between `alchemy dev` runs | Fine for tests. Note it, because some local scenarios ("restart the platform") need a deployed stage. |
| Bun-specific bundling problems | Switch to Node 24 + npm for the Alchemy CLI only, and keep Bun as the package manager. |

they can be re-run.

| Item | Value |
|---|---|
| `alchemy` version | 2.0.0-beta.87 (published 2026-11-12) |
| `@alchemy.run/cloudflare` version | 2.0.0-beta.87 |
| `effect` version | 4.1.5 (alchemy peer: ^4.1.4) |
| `@effect/platform-bun` / `@effect/platform-node` | 4.1.5 / 4.1.5. `platform-node` was **added** in `spikes/` during this spike: `alchemy dev` fails without it (see Gotchas). |
| `@alchemy.run/test` version | 2.0.0-beta.87 |
| Bun version | 1.4.5 (workspace uses the isolated linker: each package must declare what it imports) |
| Cold deploy time / no-op deploy time | Cold (first deploy of `dev_$USER`): 8.2 s wall, 6.4 s apply. Code-change redeploy: 9.4 s wall, 5.4 s apply (514.73 KB bundle). No-op: 3.7 s wall, 176 ms apply. Plan alone ≈ 1.3–3.0 s. Local `alchemy dev` start ≈ 2.5 s. Cloud test suite (deploy + test + destroy): 11.4 s. |
| HTTP import paths | `effect/http/HttpServerRequest` (`HttpServerRequest` tag, named export) and `effect/http/HttpServerResponse`, not `effect/unstable/http`. Test client: `effect/http/HttpClient`. |
| How a Worker is referenced from a Stack | Default-export the `Cloudflare.Worker(...)` value, import it in `alchemy.run.ts`, and `yield*` it inside the Stack's generator: `const api = yield* SpikesApi; return { url: api.url }`. The import alone does nothing: a resource declaration is only a description until it is yielded. The DO needs no entry in the Stack: `yield* Counter` inside the Worker's construction phase registers the binding and the `exports` entry (deploy log: `durable objects [{"logicalId":"Counter","className":"Counter"}]`, `newSqliteClasses:["Counter"]`). Source: alchemy.run/cloudflare/compute/workers, /cloudflare/tutorial/part-2, /cloudflare/compute/durable-objects. |
| How `fetch` reads the request path | `const request = yield* HttpServerRequest` inside `fetch`. `request.url` is path + query with the host stripped (`removeHost` in `effect/dist/http/HttpServerRequest.js` `fromWeb`). The Worker uses `new URL(request.url, "http://local").pathname` to drop the query. |
| Is `workersDev: true` needed? | No. `workersDev` defaults to `true` (stable `workers.dev` URL + version previews), per `WorkerProps.workersDev` in `@alchemy.run/cloudflare/lib/Workers/Worker.d.ts`. The deploy log shows `Enabling workers.dev subdomain...` with no prop set. |
| Does local DO state persist across `alchemy dev` restarts? | **Yes.** It is SQLite under `spikes/.alchemy/local/<worker-physical-name>-Counter/*.sqlite`. Before the restart: increment, increment → 1, 2. After the restart: `get` → 2, `increment` → 3. State is keyed by stage (through the physical name), so `local_$USER` and `test_$USER` (dev mode) have separate local counters. |
| Does deployed DO state survive a redeploy? | Yes. Before: increment ×3 → 3. Redeploy with `v: 2` added to the response. After: `get` → `{"name":"a","count":3,"v":2}`. |
| Bun test adapter | `@alchemy.run/test/Bun` works, so the Vitest fallback wasn't needed. It passes locally (`ALCHEMY_TEST_DEV=1`, url `http://localhost:1337`) and in the cloud (`test_$USER`). |
| `alchemy init` / `create` | The beta.87 CLI has no `init`/`create` subcommand (`alchemy --help` lists provider, deploy, dev, destroy, plan, logs, profile, state, drift). Getting-started uses the package manager's own `init`. The hand-made layout stands. |
| Gotchas | (1) Run the CLI from the root with `bun run <dev\|deploy\|plan\|destroy\|alchemy …>`, which runs `bun --bun alchemy` inside `spikes/`. `bunx alchemy` at the root downloads a temporary copy that can't find `@effect/platform-bun`. Running `node_modules/.bin/alchemy` directly uses Node, which needs `@effect/platform-node`. (2) **`alchemy dev` imports `@effect/platform-node` even under Bun** (`alchemy/src/Workers/Workerd/WorkerBridge.ts`). It is an *optional* peer of `alchemy`, so nothing warns at install time; dev fails with `Cannot find package '@effect/platform-node'`. Fix: depend on it in `spikes/`. (3) **`alchemy dev` and `alchemy deploy` share per-stage state.** `dev` defaults to `dev_$USER`, the same stage the spikes deploy to. After a dev run, plan shows `[SpikesApi] replace (local → live)`. The docs say `dev --stage X` "replaces that stage's local/live mode", so running dev on `dev_$USER` would replace the deployed Worker with a local one. The root `dev` script now passes `--stage local_$USER`. (4) The sketch's `HttpServerResponse.json(...)` returns `Effect<HttpServerResponse, HttpBodyError>`, so it must be `yield*`ed (`text` is plain). (5) A destroyed `workers.dev` URL kept answering 200 for a few seconds, then returned 404 / CF error 1042. (6) A fresh `workers.dev` URL can 404 briefly: the test uses `Test.getWhenReady`. (7) `bun --cwd spikes test` runs a *script* named `test`, not the test runner, so the root scripts use `cd spikes && bun test`. (8) The docs' `WorkerProps.workersDev` comment mentions `previewsEnabled`, but the type's field is `preview`. |

### Sketch corrections

- Worker: `HttpServerResponse.json` must be `yield*`ed. Read the path from `yield* HttpServerRequest`, imported as a named export from `effect/http/HttpServerRequest`.
- Stack: as sketched. `yield* SpikesApi` with the default import is correct.
- Test: as sketched, plus `afterAll(destroy(Stack))` so the cloud stage is cleaned up, and `Test.getWhenReady` for the first request. Use a fresh DO name per run, because cloud state persists between runs until the stage is destroyed.
- Layout: no `tsconfig.base.json` or `bunfig.toml` changes were needed. No test preload.
