# Spike 0.3: Durable callbacks

**Question:** is `Alchemy.makeCallback` a reliable enough scheduler to drive the inbox drain
loop (M1), the outbox (M3), and the step-by-step LLM loop (M2)?

**Timebox:** 1 day. **Size:** M. **Depends on:** 0.1. **Informs:** D3, D4, D6, D7.

## Why it matters

Decision D4 says nothing polls: every state change that needs follow-up work schedules a durable
callback **in the same storage transaction**. The design is only correct if:
- scheduling is atomic with the write,
- delivery is at least once and survives redeploys and evictions,
- failures are retried with a known policy, and
- we understand when a callback can run concurrently with other calls to the same DO.

If any of those fail, we fall back to the raw DO `alarm` plus our own schedule table.

## What the docs say (2026-11-25)

```ts
const onSnapshot = yield* Alchemy.makeCallback(
  "snapshot",
  Effect.fn(function* (payload: { revision: string; body: string }) { /* ... */ }),
  { retry: { delay: "10 seconds" } },
);
yield* state.storage.transaction(Effect.gen(function* () {
  yield* onSnapshot.schedule(revision, { after: "30 seconds", payload: { revision, body } });
}));
yield* onSnapshot.cancel(revision);
```

- Register it in the DO's **inner (per-instance) Effect**. Registering in a Worker or in the
  construction phase isn't supported.
- Payloads must be JSON. `Date`, `undefined`, and `BigInt` are rejected.
- Delivery is at least once. `schedule` takes `at` or `after`. Scheduling the same (name, id)
  again **replaces** the pending job.
- Callback names and payload formats are **persisted contracts**. Renaming a handler does not
  migrate pending jobs.
- It shares the single native alarm with legacy `alarm` / `scheduleEvent`.

## Probe setup

Create a `Probe` DO in `spikes/src/probe.ts` with:
- an append-only `log` table in DO SQLite: `(seq, at, event, id, attempt, detail)`
- a callback `"work"` whose payload is `{ id, failTimes, sleepMs }`. It logs `start` and `end`, and
  throws while the stored attempt count is below `failTimes`
- RPC methods: `schedule(id, opts)`, `scheduleInTxThenFail(id)`, `cancel(id)`, `log()`, `reset()`

Routes go under `/probe/:name/...`. Every experiment reads `GET /probe/:name/log` to see what
happened. Run each experiment locally (`alchemy dev`) **and** on the deployed stage. Local and
deployed behavior may differ.

## Experiments

| # | Experiment | What to look at |
|---|---|---|
| E1 | Schedule `after: "2 seconds"` and check it fires | Delay accuracy; how long it takes when the DO was idle or hibernated |
| E2 | Schedule inside `storage.transaction`, then fail the transaction | **Atomicity**: the callback must not fire. This is the most important result. |
| E3 | `failTimes: 3` with `retry: { delay: "2 seconds" }` | Retry count and spacing; whether there's backoff; **whether it ever gives up** (or retries forever?); is the attempt number visible to the handler? |
| E4 | Schedule the same id twice with different payloads | Replace semantics: only the second runs |
| E5 | Schedule `after: "60 seconds"`, then **redeploy** with a changed handler (it logs `v2`) | It fires after the redeploy and runs the **new** code |
| E6 | Schedule a callback, then redeploy with that **callback name removed** | What happens to the orphaned job: dropped, error, retried forever? |
| E7 | Schedule 100 callbacks with `after: 0` in one transaction | All fire; in what order; are they serialized or interleaved; how long in total |
| E8 | Callback with `sleepMs: 5000` (awaiting a `fetch` or a timer) while HTTP calls hit the same DO | **Concurrency**: can RPC calls run while a callback awaits I/O? (DO input gates.) Is the drain loop single-flight without our own lock? |
| E9 | Callback that schedules itself again (a chain of 10) | Self-rescheduling works (the drain loop pattern) |
| E10 | CPU-heavy callback (busy loop for 1s, 10s, 30s) | Where the CPU limit is hit and what the error is. Feeds 0.6 |
| E11 | Callback whose handler fails with a tagged error vs a defect (`Effect.die`) | Do both retry? Do we need our own retry policy for permanent errors? |
| E12 | Payload with a `Date` or `undefined` | Rejected at schedule time? (Confirms the JSON-only contract) |

## Design consequences to decide afterwards

- **Drain loop (M1):** "enqueue writes a row and schedules `drain` (id = `"drain"`, after 0) in the
  same transaction." Given E4's replace semantics, many enqueues collapse into one pending drain.
  Make sure replacing an **in-flight** drain doesn't drop work. The drain should re-check the
  table and reschedule itself if rows are left (E9).
- **Our retry policy vs theirs:** if E3 shows unbounded retries, the framework should catch
  handler errors itself and mark `attempts` in the inbox row. The callback then always succeeds,
  and our backoff becomes `schedule(after: backoff)`. Most likely, our inbox owns retries and the
  callback is only a wake-up.
- **Concurrency (E8):** if RPC can interleave with a running callback, every state transition
  needs `storage.transaction` and a `status = 'running'` guard.
- **Versioning (E6):** callback names are part of the framework's persisted contract. Keep the
  set small and stable (`drain`, `deliver`, `step`) and version payloads (`{ v: 1, ... }`).

## Fallback

The raw DO `alarm()` plus a `schedule` table we own (`id, run_at, kind, payload, attempts`).
The alarm is set to `min(run_at)`. That's more code, but every behavior is under our control.
Alchemy says legacy `alarm` handlers still work alongside callbacks.
