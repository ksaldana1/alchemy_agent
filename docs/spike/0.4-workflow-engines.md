# Spike 0.4: Workflow engine bake-off

**Question:** should `AgentWorkflow` (M5) build on **native Cloudflare Workflows** or on
**`effect/workflow` with Alchemy's Durable Object engine**?

**Timebox:** 1.5 days. **Size:** M. **Depends on:** 0.1, 0.3. **Informs:** D9.

## Why it matters

A workflow in this framework mostly does one thing: **call an agent task and wait for its result,
durably**, sometimes several in parallel, plus timers and human approvals. Two engines can do
this, and they differ in how a running workflow gets signaled, how replay works, and how well the
types flow. The public API (`AgentWorkflow.make`, `AgentWorkflow.call`, `waitFor`, `sleep`) should
stay the same either way. This spike picks what goes underneath.

## The two candidates (from the docs, 2026-11-25)

**Native: `Cloudflare.Workflow`.** Replay-based: the body re-runs from the top, and finished
steps return their stored results.

```ts
export default class Publish extends Cloudflare.Workflow<Publish>()(
  "Publish",
  Effect.gen(function* () {
    return Effect.fn(function* (input: { path: string }) {
      const taskId = yield* Cloudflare.Workflows.task("enqueue-edit", enqueueEffect);
      const done = yield* Cloudflare.Workflows.waitForEvent<Result>("edit-done",
        { type: `task:${taskId}`, timeout: "1 hour" });
      return done;
    });
  }),
) {}
// signal from elsewhere: (yield* Publish).get(instanceId).sendEvent({ type, payload })
```

**Effect: `effect/workflow` + `alchemy/Workflows`** on `Cloudflare.Workflows.layerDurableObjectEngine()`.

```ts
export const Publish = Workflow.make("Publish", {
  payload: { path: Schema.String }, success: Result, idempotencyKey: ({ path }) => path,
});
export const PublishLive = Workflows.layer(Publish, Effect.fn(function* ({ path }) {
  yield* Activity.make({ name: "enqueue-edit", success: Schema.String, execute: enqueueEffect });
  return yield* DurableDeferred.await(EditDone);
}));
// signal: (yield* Workflows.RunWorkflow(Publish)).get(executionId) → run.signal(EditDone, value)
```

## Scenario (build it in both engines)

A `Worker` agent DO (from 0.3, using the callback pattern) has a task `work({ n, failTimes })`
that finishes after about 2 seconds through a durable callback. When it finishes, the DO
**signals the workflow** that is waiting on it.

The workflow, `Pipeline({ n })`:
1. Step `call-a`: enqueue `work` on agent `a` with deterministic `taskId = <instanceId>:0`.
2. Wait for `a`'s completion signal.
3. In parallel: enqueue to agents `b` and `c` (`:1`, `:2`) and wait for both.
4. `sleep("cooldown", "5 seconds")`.
5. Wait for an external `approve` signal sent over HTTP, with a 2-minute timeout.
6. Return `{ a, b, c, approved }`.

Routes go under `/wf/<engine>/...`: start, status, approve.

## Comparison criteria

Score each criterion for both engines and write down the evidence.

| # | Criterion | How to test |
|---|---|---|
| W1 | Input/output types inferred at `start` and at `result`/`status` | Type tests (`expect-type`) |
| W2 | **A DO can signal a waiting workflow** | Does a DO get a workflow binding (`yield* Pipeline` inside a DO)? Can it reach an execution by id? |
| W3 | **Signal before wait** (the agent finishes before the workflow reaches the wait) | Make the agent's task instant. Is an early event buffered, or lost? A lost event means we'd need re-check-on-wait logic. |
| W4 | Duplicate signal | Send it twice. The second must be a no-op or harmless. |
| W5 | Replay safety | Count how many times `enqueue` runs per call under chaos (make step 3 throw once). Must be exactly 1 enqueue per taskId, or dedupe must make extra ones harmless. |
| W6 | Redeploy mid-wait | Redeploy during step 2 and during the step 4 sleep. The workflow completes. |
| W7 | Code change mid-run | Redeploy with step 3 reordered. What does each engine do (fail, nondeterminism error, silently continue)? |
| W8 | Parallel waits | `Effect.all([waitB, waitC], { concurrency: "unbounded" })` works with both engines |
| W9 | Timeout | Don't approve. Step 5 times out with a catchable, typed error. |
| W10 | Local dev | Runs under `alchemy dev` with real step semantics, and in `Test.make({ dev: true })` |
| W11 | Observability | Status API, list of steps, dashboard visibility, error details |
| W12 | Limits | Steps per instance, payload/result size, max wait duration, concurrency per account. Copy to 0.6. |
| W13 | Idempotent start | Starting with the same key or id twice returns the same instance |
| W14 | Ergonomics | Lines of code for the scenario; how much a user must know about replay |

## Decision guide

- If **W2, W3, or W5** fails for an engine, that engine is out, unless there is a cheap workaround.
- Prefer **native** if it's equal or better on W2–W6: platform dashboard, metrics, and limits
  managed by Cloudflare.
- Prefer **Effect** if W1/W14 are clearly better and W6/W7 behave well. It also keeps workflow
  state in a DO we control, so it fits D3/D7.
- Either way, `AgentWorkflow.call` hides the signal mechanism. Write down the exact
  "agent completes → signal workflow" hook the inbox will need in M1 (e.g. an `onSettled`
  subscriber list stored with the inbox row).

## What changed before the spike ran (2026-11-26)

Alchemy beta.87 ships **both engines behind Effect's own `effect/workflow` API**:
`Cloudflare.Workflows.layerDurableObjectEngine()` and `Cloudflare.Workflows.NativeEngine` are
both `WorkflowEngine` Layers. A workflow is written once (`Workflow.make`, `Workflows.layer`,
`Activity`, `DurableDeferred`, `DurableClock`), and the engine is a Layer the Worker provides. So
the bake-off compared engines under identical code, not two APIs.

M3 had also built most of the "agent completes → signal workflow" hook: agents already keep
subscribers and deliver replies through their outbox. The spike added one more kind of
subscriber, a workflow run.

## What was built

- **Library (engine-agnostic, the M5 foundation):** `packages/agent/src/internal/workflow.ts`.
  Inside a workflow run, `(yield* Job.client)(name).Work(payload)` is a durable call:
  1. An Activity `agent-call/c<n>` enqueues the task (id `wf/<Workflow>/<executionId>/c<n>`, or
     the Rpc's `primaryKey`) and subscribes with reply-to `workflow:<Workflow>` /
     `<executionId>` / `agent-call/c<n>`. It records which call it made, plus the record if the
     task had already settled.
  2. `DurableDeferred.await(agent-call/c<n>)` waits. The agent's outbox delivers the reply
     with the engine's `deferredDone` (`outbox.ts`, `signalWorkflow`).
  3. The record becomes the success, the declared error, or an `AgentError`, exactly as for
     any client.
  The agent finds the engine in its construction context, so the Worker must provide the engine
  *to* the agents: `Layer.mergeAll(agents, workflows).pipe(Layer.provideMerge(engine))`.
- **Spike:** `spikes/src/wf/pipeline.ts` (one Worker per engine, a `Job` agent, and the
  `Pipeline` workflow), `spikes/test/workflows.test.ts` (4 scenarios × 2 engines, local and
  cloud), and `spikes/scripts/wf-redeploy.ts` (W6).

## Findings

All results are from 2026-11-26, local workerd (`ALCHEMY_TEST_DEV=1`) and deployed (`test_$USER`, plus `dev_$USER` for W6).

| # | Native Cloudflare Workflows (`NativeEngine`) | effect/workflow + DO engine (`layerDurableObjectEngine`) |
|---|---|---|
| W1 | Same code, same types: `Workflow.make` payload/success/error type `RunWorkflow(...).start` and `run.status`; agent calls are typed by their Rpcs. | Same. |
| W2 | ✅ An agent DO signals a waiting run with `engine.deferredDone` → `instance.sendEvent`. | ✅ `engine.deferredDone` → the execution DO's `deferredDone` RPC. |
| W3 | ✅ A signal sent before the run reaches the wait is kept: Cloudflare buffers events. The agent call path doesn't depend on it, because the send step returns an already-settled record. | ✅ Kept: the completion is stored in the run's journal (`workflow_deferred`). |
| W4 | ✅ A second, different signal is ignored. | ✅ Ignored (`INSERT OR IGNORE`). |
| W5 | ✅ Each call is one task with `attempts: 1` and the run's causation. The run replays after each wait, and the send step is replayed from `step.do`. | ✅ Same. The run replays from the top on every wake-up (≥ 5 times here), and the send step's journal entry is reused. |
| W6 | ✅ A `--force` redeploy while waiting for approval, then approve: completes, each call `attempts=1`. | ✅ Same. |
| W7 | Not run. By code: steps are journaled by name, so a reordered workflow replays silently. **Fixed for agent calls:** the send step records which call it made, and a different call at that position dies with an error. Other activities are as Effect makes them. | Same, and the same guard applies. |
| W8 | ✅ `Effect.all` of two agent calls, both waiting at once. | ✅ |
| W9 | ❌ **No durable timeout.** `DurableDeferred.raceAll` (and `Activity.raceAll`) die: "aren't supported on Cloudflare Workflows" (`NativeEngine.ts`, `deferredResult`). A wait can only be unbounded. | ✅ `DurableDeferred.raceAll([await(Approve), DurableClock.sleep(timeout)])` returns `"timeout"`. |
| W10 | ✅ Runs under local workerd (`Test.make({ dev: true })`). | ✅ |
| W11 | Cloudflare dashboard: instances, steps, and errors, plus our status API. | Only what we build: `run.status`, the journal in each execution's SQLite. |
| W12 | 365-day maximum wait (the engine's `SIGNAL_TIMEOUT`); a 10-minute default step timeout (`withStepConfig`). Step count and payload limits weren't checked. | No step timeout. A run is a DO callback, so it has a DO's CPU limits (0.6) per replay. |
| W13 | ✅ The same key gives the same execution id, and one run. | ✅ |
| W14 | Identical workflow code; the engine is one Layer. The native engine forbids `raceAll`. | Identical; no restrictions met. |

Other findings:
- **`Workflow.make(tag, options)`** is Effect 4.1's signature. NORTH-STAR.md's
  `Workflow.make({ name, … })` was wrong, and has been fixed.
- **A client call inside an `Activity`** would see a `WorkflowInstance` and try to journal a
  nested step. The workflow path should skip it inside activities (M5).
- **The engine must be in the agents' context** for replies to reach runs. `Platform.make`
  should do this wiring so users don't.

**Decision (D9):** write workflows with `effect/workflow` (Effect's own API, as the north star
already does), and run them on **Alchemy's Durable Object engine** by default. It's the only
engine with durable timeouts (W9), which M5's `waitFor(…, timeout)`, M7's human requests, and
the deferred wait timeouts from M3 all need. It also keeps workflow state in Durable Objects, like
everything else here (D3, D7). The native engine passed everything else, including redeploys, and the
engine is just a Layer. So a deployment that wants Cloudflare's dashboard can switch to it for
workflows that don't race.
