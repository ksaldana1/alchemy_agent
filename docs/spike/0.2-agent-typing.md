# Spike 0.2: Agent typing

**Question:** can `Agent.make` wrap `Cloudflare.DurableObject` so that task names, inputs, and
outputs are inferred from the definition, both for code holding a stub and for the API client,
without depending on Alchemy internals?

**Timebox:** 1–1.5 days. **Size:** M. **Depends on:** 0.1. **Informs:** D1, D2.

## Why it matters

The selling point of the library is "define an agent once, and every call site is typed." The
reference repo gets this from `defineAgent` + `TaskRef`s (see
`mini-agent-runtime/src/lib/agent.ts` and `tests/library-refs.test.ts`). On Cloudflare, the agent
is an Alchemy DO class, and Alchemy infers RPC types from the object the inner Effect returns. We
need to know how far that inference stretches before choosing the public API shape.

## Target shape (to validate)

```ts
// One agent definition = one DO class (D2).
export class Echo extends Agent.make<Echo>()("Echo", {
  tasks: {
    echo: Agent.task(
      { input: Schema.Struct({ text: Schema.String }) },
      ({ text }) => Effect.succeed({ echoed: text.toUpperCase() }),
    ),
    count: Agent.task(
      { input: Schema.Struct({ n: Schema.Number }) },
      ({ n }) => Effect.gen(function* () {
        const ctx = yield* AgentContext;          // framework-provided service
        return { n, by: ctx.agent.name };
      }),
    ),
  },
}) {}

// From another Worker or DO:
const echo = yield* Echo;                                   // Alchemy binding
const handle = yield* echo.getByName("a").enqueue("t1", "echo", { text: "hi" });

// Helper types:
type N = TaskNames<typeof Echo>;                            // "echo" | "count"
type I = TaskInput<typeof Echo, "echo">;                    // { readonly text: string }
type O = TaskOutput<typeof Echo, "echo">;                   // { echoed: string }
```

The `<Self>()` double call mirrors `Cloudflare.DurableObject<Self>()(...)`. Check whether
`Agent.make` needs the same pattern, or whether `Agent.make("Echo", {...})` can return the class
directly.

## Approaches to try, in order

**A. Generic RPC method.** The inner Effect returns
`{ enqueue: <K extends keyof Tasks>(taskId: string, task: K, input: Input<Tasks[K]>) => Effect<...> }`.
Question: does Alchemy's stub type keep the generic, or flatten it to a union / `any`?

**B. One RPC method per task.** Build the returned object from `tasks` with a mapped type:
`{ [K in keyof Tasks]: (taskId, input) => Effect<TaskHandle<Output>> }`. Mapped types usually
survive inference better than generic methods. Downside: task names share a namespace with
framework methods like `status` and `result`. Mitigation: nest them under `tasks`, if nested
objects are supported over RPC (probably not, so test it), or use a prefix.

**C. Framework-owned typed client.** The DO exposes one untyped method,
`enqueue(taskId: string, task: string, input: unknown)`. The library wraps the stub:
`Agent.client(Echo, stub)` (or `Echo.named("a")`) returns a typed facade whose types come
**from the definition object**, not from Alchemy's RPC inference. Input is validated with the
task schema on both sides. This is the most robust option and doesn't depend on Alchemy internals.

Expected outcome: **C for the public API**, possibly with A or B underneath if they work. Record
which ones actually typecheck.

## Things to check along the way

1. **Static access to the definition.** Can `Agent.make` attach the definition to the class as a
   static (`Echo.definition`) so that `TaskInput<typeof Echo, K>` can read it? Does Alchemy's
   class factory let us add statics, or do we need to return `class extends Base { static def }`?
2. **Service requirements (R).** A handler that `yield*`s a service the framework doesn't
   provide (e.g. `Workspace` before M4) must be a compile error at `Agent.make`, not at runtime.
   Make the error message readable.
3. **Schema `Type` vs `Encoded`.** Callers pass the encoded form (JSON-safe). Handlers receive the
   decoded type. Make sure the helper types expose both, e.g. `TaskInput` (encoded) and
   `TaskInputDecoded`, and choose the default.
4. **Output must be JSON-serializable.** Decide whether tasks also declare an `output` schema
   (stricter, enables validation and stored results) or infer output from the handler's return
   type (lighter). Try both. Recommendation to validate: optional `output` schema, and inferred
   when absent.
5. **Errors.** Handler error channel `E`: does `PermanentError` remain a tagged error in the type?
6. **Bundling.** An agent module is imported by the Worker (for the binding) and is also the DO's
   code. Check that this doesn't create an import cycle or duplicate bundle.
7. **Editor experience.** Hover over `enqueue(...)` in the editor. Are the types readable, or a
   wall of Alchemy generics?

## Runtime behavior for this spike (minimal)

There's no inbox yet. `enqueue` validates input with the schema, runs the handler right away,
stores `{ status, result }` under `task:<taskId>` in DO storage, and returns `{ taskId }`.
`result(taskId)` reads it back. That's enough to prove the deployed call path. The real inbox
comes in M1.

Route: `POST /echo/:name/tasks { taskId, task, input }`, `GET /echo/:name/tasks/:taskId`.

## Type tests

Use `expect-type` and run them with `tsc --noEmit`. Bun's test runner doesn't check types.

```ts
// spikes/test/types/agent.test-d.ts
expectTypeOf<TaskNames<typeof Echo>>().toEqualTypeOf<"echo" | "count">();
expectTypeOf<TaskInput<typeof Echo, "echo">>().toEqualTypeOf<{ readonly text: string }>();
expectTypeOf<TaskOutput<typeof Echo, "echo">>().toEqualTypeOf<{ echoed: string }>();

declare const client: AgentClient<typeof Echo>;
// @ts-expect-error unknown task
client.send("nope", {});
// @ts-expect-error wrong input
client.send("echo", { text: 1 });
// @ts-expect-error handler requires a service the framework doesn't provide
Agent.make("Bad", { tasks: { t: Agent.task({ input: Schema.Struct({}) }, () => Workspace) } });
```

## Risks and fallbacks

| Risk | Fallback |
|---|---|
| Alchemy's class factory doesn't allow a wrapper to stay typed | C, plus an explicit type parameter: `Agent.make<typeof def>(...)` |
| Cross-DO typed references cause circular imports (A ↔ B) | Reference by a type-only import plus the name (`Agent.ref<typeof Reviewer>("Reviewer")`), resolving the binding at runtime |
| Inference gets too slow in large agents | Require an explicit `output` schema per task |

## Findings

Run 2026-11-25 on the pinned versions. Code: `spikes/src/agent.ts` (the throwaway `Agent` module),
`spikes/src/echo.ts` (agent A), `spikes/src/relay.ts` (agent B), and the `/echo` and `/relay` routes
in `spikes/src/worker.ts`. Type tests: `spikes/test/types/agent.test-d.ts`, checked by
`bun run typecheck`. Runtime tests: `spikes/test/agent.test.ts`, which pass locally
(`bun run test`) and on `test_$USER` (`bun run test:cloud`). Deployed on `dev_$USER` under `/echo`
and `/relay`.

| Question | Answer |
|---|---|
| Does approach A (generic RPC method) keep its types? | **Yes.** `DurableObjectStub<Shape>` is a plain mapped type, `{ [k in keyof Shape]: Shape[k] }` (`@alchemy.run/cloudflare/lib/Workers/DurableObject.d.ts`), so a generic `enqueue<K extends keyof Tasks>` survives unchanged. On the raw stub, `stub.enqueue("t1", "nope", {})` and a wrong input are compile errors (type tests). The cost is readability: hovering the stub shows `input: { echo: TaskDef<Struct<{ readonly text: String; }>, …>; count: TaskDef<…> }[K]["input"]["Encoded"]`. |
| Does approach B (mapped methods) keep its types? Are nested objects allowed over RPC? | Flat mapped methods (`task_echo(taskId, input)`) keep their types, for the same mapped-type reason. **Nested objects are rejected at compile time**: the implementing overload constrains `Shape extends MainRpc<DurableObjectState>`, an index signature whose values must be an Effect, a Stream, or a function returning one. The error reads `Property 'tasks' is incompatible with index signature`. At runtime the bridge only dispatches top-level own keys and dies on anything else (`alchemy/src/Workers/DurableObjectBridge.ts`, `dispatch`). B wasn't pursued further, because task names would share the namespace with `result`, `fetch`, `alarm`, and so on. |
| Chosen approach | **C for the public API, with A underneath.** The DO exposes a generic `enqueue` (A), so even raw-stub callers are type-checked. Users get `Agent.client(Echo, stub)` → `AgentClient<typeof Echo>`, whose types come from the static definition: `send<K extends TaskNames<Ag>>(taskId, task: K, input: TaskInput<Ag, K>)`. It hovers as written, validates input against the schema before the round trip, and decodes outputs that have an `output` schema. Alchemy types relied on: `Cloudflare.DurableObject<Self>()(name, impl)` (the implementing overload), `DurableObjectStub<Shape>` (mapped type), the `MainRpc` constraint, `Cloudflare.DurableObjectState` (`id.name`, `storage`), and `RuntimeContext` from `alchemy/RuntimeContext`. No Alchemy internals: C needs only an object with `enqueue` and `result` methods. |
| Can we add statics to the Alchemy DO class? | **Yes.** `Agent.make` returns `Object.assign(base, { definition })`, and `class Echo extends Agent.make<Echo>()(…) {}` inherits the static. `typeof Echo` carries `definition`, which every helper type reads (`TaskNames`, `TaskInput`, `TaskInputDecoded`, `TaskOutput`, `TaskError`). At runtime, `Relay.definition` is what the Worker's client validates against. `yield* Echo` still works on the subclass. |
| `Agent.make<Self>()` double call? | Needed, for the same reason as Alchemy: `Self` must be explicit while `Name`, `Tasks`, and `Uses` are inferred, and TypeScript can't mix explicit and inferred type arguments in one call. `Agent.make("Echo", {...})` without `Self` can't produce the stub type, because `DurableObject<Self>` needs the class. |
| Is the missing-service error readable? | **Yes, once it's custom.** `tasks` is typed as `Tasks & CheckServices<Tasks, Allowed>`: each task whose `R` isn't covered becomes a string literal type. Real error for a handler that yields a `Workspace` service: `Type 'TaskDef<Struct<{}>, undefined, string, never, Workspace>' is not assignable to type '… & "Task \"t\" needs a service the framework does not provide"'`. That names the task and shows `Workspace` in the `R` slot. The same check rejects `Agent.use(Echo)` when `Echo` isn't listed in `uses`. Allowed services: `AgentContext`, `RuntimeContext` (calling another agent's stub requires it), and `AgentRef<Name>` for each agent in `uses`. |
| Output: declared schema, inferred type, or both | **Both.** `Agent.task({ input }, handler)` infers the output from the handler (`TaskOutput<Echo, "echo">` = `{ echoed: string }`). `Agent.task({ input, output }, handler)` requires the handler to return `output.Type`, stores `output.Encoded` (proved at runtime: `Date` → `"1970-01-01T00:00:00.000Z"`), and the client decodes it back (`TaskOutput` = `{ readonly at: Date }`). A JSON-safety check for inferred outputs isn't built yet; it's needed before M1. |
| Encoded vs decoded input | `TaskInput` is the **Encoded** form and is the default, because callers send JSON. `TaskInputDecoded` is what the handler receives. Both are type-tested. Task schemas must have no decoding/encoding services (`Schema.Codec<any, any, never, never>`), since they run on both sides. |
| Errors | A handler's `E` stays typed: `TaskError<Relay, "fail">` = `PermanentError`. Errors cross RPC and storage as plain `{ _tag, message, … }` objects without their class. `Effect.catchTags` in the Worker still matches them: `UnknownTaskError` and `TaskInputError` came back as HTTP 400 locally and deployed. `TaskRecord` types failures as `TaskFailure<E>` (tag plus message, or `Defect`) rather than claiming class instances. Alchemy can revive classes through the `errors` prop, but **only the declaration overload `DurableObject<Self, Shape>()(name, props)` accepts it**. The implementing overload `(name, impl)` takes no props. |
| Cross-DO reference pattern | `Agent.make<Relay>()("Relay", { uses: [Echo], tasks })`. `Agent.make` runs `yield* Echo` for each entry in the DO's construction phase (the only place Alchemy allows bindings), and provides one `AgentRef<"Echo">` service per entry to handlers. A handler calls `const echo = yield* Agent.use(Echo); echo.getByName(n).send(…)`, typed through `AgentClient<typeof Echo>`. Proved deployed: Relay `r` → Echo `relay-r` → `{"echoed":"VIA RELAY"}`. A DO yielding another DO's class is allowed: its `Req` is `Worker`, which is among `DurableObjectServices`. Echo bound from both the Worker and Relay produced a single binding (plan: `2 binding changes` for Echo and Relay). Circular A ↔ B wasn't tried; the type-only `Agent.ref` fallback in the risks table still stands for M3. |
| Bundling | No cycle and no duplicate. The agent module is imported by the Worker (for the binding), by Relay (`uses`), and is the DO's code. The bundle went from 514.73 KB to 520.35 KB with `agent.ts`, `echo.ts`, and `relay.ts` added. |
| Editor experience | Client (C) hover: `<K extends TaskNames<typeof Echo>>(taskId: string, task: K, input: TaskInput<typeof Echo, K>) => Effect<TaskHandle<K>, TaskInputError \| UnknownTaskError, RuntimeContext>`, which is readable. Raw stub (A) hover is a wall of `TaskDef<Struct<…>>` (see row A). `stub.result` hovers as `AnyTaskRecord<{ echo: TaskDef<…>; count: TaskDef<…> }>`. |
| Agent name inside the DO | `state.id.name` holds the `getByName` name, locally and deployed (`count` returned `"by": "a"`). `AgentContext` provides it. |
| Gotchas | (1) `AgentShape` must be a `type`, not an `interface`: interfaces aren't assignable to `MainRpc`'s index signature. (2) `TaskDef` is invariant in its input schema (it's both a property and the handler's parameter type), so the "any task" type must use `any` there, not `Schema.Codec<any, any>`. (3) **A DO method's `R` leaks into the stub type**: storage calls need `RuntimeContext`, so every stub method returns `Effect<…, …, RuntimeContext>`, and so does every handler that calls another agent. (4) **TypeScript 7.0.2 hides later errors in a file while earlier ones are present.** A probe with all `@ts-expect-error`s stripped showed only the first 4 errors. Removing the directives one group at a time showed the rest, including one test that was passing for the wrong reason (`Workspace.asEffect()` doesn't exist). Always check `@ts-expect-error` cases one group at a time. (5) In Effect 4, `Context.Key` is itself an Effect (`yield* Key`), and `Effect.service(key)` exists. A class-style `Context.Service` has no `.asEffect()`. (6) Each test file's `beforeAll(deploy(Stack))` deploys and destroys the stack separately, so `test:cloud` now does two full cycles (23 s for 2 files). |

### Carry into M1

- Public API: `Agent.make<Self>()(name, { uses?, tasks })`, `Agent.task({ input, output? }, handler)`,
  `Agent.client(Agent, stub)` / `Agent.use(Agent)`, `AgentContext`, and the helper types above.
- The DO keeps one generic `enqueue` plus `result`. With a real inbox, `result` should take the
  `TaskHandle` (task name included) so its type narrows. Today it returns the union over all tasks.
- Decide whether `RuntimeContext` belongs in user-visible handler types, or whether the client
  should provide it.
- Add a JSON-safety check for inferred outputs.
- Store failures as encoded tagged errors, and optionally revive them with the task's error
  schemas on the client.
