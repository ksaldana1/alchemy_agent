# Spike 0.7: Agents on Effect's Cloudflare cluster

**Question:** should agents be `effect/cluster` entities run by **`@effect/platform-cloudflare`**
(`CloudflareCluster`, deployed with `AlchemyCloudflareCluster.make`), with our waiting layer on
top, instead of our own inbox, drain loop, and retry machinery?

**Timebox:** 2 days (half a day of source reading, then probes). **Size:** M. **Depends on:**
M1–M8 (it's a replacement question). **Informs:** D2, D3, D4, D7, and whether the M1 inbox stays.

## Why it matters

Effect 4.1.3 added experimental Cloudflare support for cluster: one entity instance per Durable
Object, its SQLite as the system of record, persisted messages deduplicated by `primaryKey`,
`DeliverAt`, per-entity `concurrency`, alarm-driven replay after eviction, a `SqlClient` per
entity, `Entity.makeTestClient` for tests, a workflow engine and persisted queues on DOs, and an
Alchemy v2 deploy path (`peerDependencies: @alchemy.run/cloudflare >=2.0.0-beta.85`). Our M1 inbox
does much of the same by hand.

It doesn't do what makes agents different. Its README ("Long waits and delivery", "Handler
concurrency") says an ask pins the caller, a caller's eviction drops its wait, an A → B → A ask
cycle deadlocks at the default concurrency, and durable long waits belong in a workflow. Our
outbox does exactly that: a recorded call, a task that waits holding no execution, a reply
delivered as a message, and the handler run again with the recorded answers. So did LLM turns.

The bet: build agents as entities and keep only the waiting layer (outbox, subscribers, turns,
suspension), so the framework is smaller and stays on Effect's own runtime as it matures. The
library is unpublished, has no users, and its stored data can change freely, so this is the
cheapest time to find out.

## The candidate mechanism (to confirm)

- An agent type is an `Entity`; a task is a `Persisted` Rpc; the task id is the `primaryKey`.
- A call between agents is a **tell** (`discard: true`) recorded in the caller's outbox, never an
  ask. The answer comes back as a tell to the caller (`Reply` Rpc), which re-runs the waiting
  task. Nothing waits in memory, so cycles can't deadlock.
- A waiting task ends its execution **without replying**. The question is what the runtime then
  does with an unreplied persisted request: replay it on a timer (cost per waiting task), only on
  the next message (free), or something we control.
- LLM turn steps are `DeliverAt` tells to the agent itself, or stay our own callback.
- Our framework tables (outbox, subscribers, turns, transcript) live in the entity's
  `DurableObjectSqlClient`, ideally in the same transaction as the mailbox's reply.

## Decision guide

- **Adopt** if C1 holds (a waiting task costs nothing until its reply arrives), and C3 and C5
  hold or can be built from tells plus our outbox. Then the plan is a milestone that moves agents
  onto entities, keeping the public API (`Agent.make`, `toLayer`, `client`, `generate`) unchanged.
- **Borrow** if C1 fails (replays or alarms per waiting task) or C6 fails. Then we keep our
  runtime and take `@effect/sql-sqlite-do` for storage and the `makeTestClient` approach for
  tests.
- **Wait** if it works but the gaps are in places marked experimental that are still changing
  release to release (C8). Then we re-check at the next minor version.

## Findings

**Phase 1, source reading (2026-11-26), against `@effect/platform-cloudflare` 4.1.6 vendored in
`repos/effect`.** Paths below are relative to `repos/effect/packages/platform/cloudflare/src/`: `rt` is
`internal/entityRuntime.ts`, `mb` is `internal/entityMailbox.ts`, `st` is
`internal/entityStorage.ts`, `CC` is `CloudflareCluster.ts`.

| # | Answer | Evidence |
|---|---|---|
| C1 | **No.** A handler that returns always stores a reply for an ask (`WithExit`, rt:438-446), and a successful tell is marked processed (rt:841). The only way to leave a request unreplied is a fiber that stays suspended. That keeps a heartbeat alarm every 30 s for as long as it waits (st:154-166, `internal/entityRegistry.ts:28`), and the request is replayed on every wake, by alarm or by any incoming request (rt:1043-1046, rt:1277-1284). There is no cap and no backoff. Each such request also counts against the 4096-row mailbox cap (mb:104-117). | C2 | Only through the in-memory `Replier`, keyed by the envelope object within one handler build (`effect/src/cluster/Entity.ts:425-433`). After an eviction the request is replayed as a new envelope. Writing a reply by request id (`saveReply`, `respond`) is internal (rt:881-898). | agent report, unverified line by line |
| C3 | **Not durable.** A tell is a direct `stub.invoke` RPC (CC:363-367), with `boundedRetry` (4 retries, retryable errors only) for persisted Rpcs (`internal/transport.ts:36-39`). There's no outbox in the caller: if the caller dies mid-send, the tell is lost unless the sending request is itself replayed. | verified (CC:360-368) |
| C4 | Deduplicated by request id or primaryKey (`type/id/tag/key`, `effect/src/cluster/Envelope.ts:468-494`). A duplicate gets the stored reply, joins the running request, or starts it if it isn't running (rt:788-809, rt:1110-1158). **The payload is never compared** (mb:72-80). | C5 | **No.** Mailbox writes run in their own transaction, behind a gate that waits for any open user transaction (`internal/entitySql.ts:1-12`, rt:611-614). The handler's state commits first and the reply later; a crash in between replays the handler with its state already written. This breaks our atomicity invariant ("a state change and the scheduling of its follow-up work commit together"). | verified (entitySql.ts header) |
| C6 | Likely to coexist. Its four DO classes are ordinary Alchemy declarations: `ClusterEntity`, `ClusterWorkflow`, `ClusterDurableQueue`, `ClusterSingleton` (`AlchemyCloudflareCluster.ts:140-162`). A workflow named `Cluster` would collide with `ClusterWorkflow`. | agent report; no probe |
| C7 | Cancellation means interrupting the client fiber, which sends `stub.interrupt` (CC:437-448). Tells and scheduled runs can't be interrupted. `InterruptOnTermination` isn't read on this path. Nothing matches `Agent.cancel` (cancel by task id, from anywhere, at any time). | agent report |

**What adoption would look like.** The only workable mechanism is tells all the way through:
1. A task records its calls in our own tables (through `DurableObjectSqlClient`).
2. It sends each call as a persisted tell keyed `<owner>#c<n>`, and returns once the send succeeds.
3. The callee answers with a persisted `Reply` tell, and the caller reruns the task.

A waiting task then costs nothing. But we would still own the outbox, resending pending calls
(C3), the waiting state, the reruns, LLM turns, cancellation (C7), payload conflicts (C4), and
retention (C4). We would also lose the atomic commit of a state change with its follow-up (C5).
The cluster would replace only the inbox's storage, dedupe, and replay: roughly `internal/inbox.ts`
and the drain loop. That's the smaller part of `packages/agent`, and it would come at the cost of
an invariant.

## Decision (2026-11-26): borrow, don't adopt

C1 and C5 fail, which is the decision guide's "borrow" case. Agents stay on our runtime (D2–D4 and
D7 unchanged). Phase 2's probes aren't needed for this decision and weren't run. What we take:

- **`@effect/sql-sqlite-do`** for the storage our runtime does by hand (audit item 3). This needs
  a short probe: does it work on Alchemy's `DurableObjectState` storage, with our transactions?
- **The `makeTestClient` approach** for in-memory tests of agent handlers (audit item 11), as a
  test layer of our own.
- **Their semantics as a cross-check.** Their dedupe history is unbounded, and our `retention`
  addresses that. They don't compare payloads, and our `InputConflict` does.

Re-check when the package leaves experimental, or if "park-and-replay caller hibernation" lands.
That feature is the one that would make adoption worthwhile.
