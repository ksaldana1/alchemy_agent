# Spike 0.6: Verified facts

**Question:** what platform limits and guarantees does the design rely on, and are they true?

**Timebox:** half a day of reading, plus whatever the other spikes measure. **Size:** S.
**Informs:** all decisions.

## How to use this doc

Each row is a fact the design depends on. Fill in **Value** from official docs, or from a
measurement in another spike. Every row needs a **source** (a URL, or a spike experiment id like
`0.3/E10`) and a **checked** date. If a fact is false or worse than assumed, mark it ⚠ and note
which decision it affects.

Numbers you remember are not facts until they're checked. Cloudflare limits change often.

## Problems found

*List every ⚠ row here with the decision it affects and the proposed change.*

| Fact | Affects | Proposed change |
|---|---|---|
| ⚠ Durable callbacks retry every failure forever (parking hourly), including permanent errors and CPU overruns | D3, D4 | The inbox owns attempts and permanent failures; the drain callback catches handler errors and always succeeds (0.3 verdict) |
| ⚠ Self-rescheduling without `progress` backs off and parks | D4 (drain loop), D6 (step loop) | Every drain/step reschedule passes the last processed seq as `progress` |
| ⚠ Alchemy's Workers AI adapter swallows provider errors and has no JSON mode | D5 | Treat empty responses as retryable failures; structured output through a forced `respond` tool |
| ⚠ Alchemy's Workers AI streaming corrupts numeric tokens | M2 live endpoint | Stream persisted steps over SSE, not raw tokens; report upstream |
